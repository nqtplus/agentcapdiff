# Audit #26 — Snapshot JSON duplicate-key ambiguity

## Scope

This audit reviews JSON object-key semantics at the externally supplied snapshot trust boundary used by `diff`, including the trusted PR capability-diff workflow that loads base/head snapshot artifacts generated from static repository data.

## Finding

Python `json.loads()` accepts duplicate object keys and silently keeps the later value. For a security snapshot that behavior creates ambiguity before AgentCapDiff's structural, fingerprint, policy, and semantic validators run.

An artifact could contain two definitions of a security-relevant field such as `capabilities`, `risk_score`, `policy.deny`, or a nested graph property. The first definition would be discarded before validation, so reviewers or other JSON consumers could reason about a different representation than the one AgentCapDiff actually evaluates.

JSON escape decoding can make the ambiguity less visible. For example, `"deny"` and `"\u0064eny"` decode to the same object key even though their raw source text differs.

## Remediation

Snapshot parsing now uses a dedicated duplicate-safe JSON loader based on `json.loads(..., object_pairs_hook=...)`.

The object-pairs hook runs for every JSON object at every nesting depth and rejects a key that has already appeared in that same object. Because duplicate detection receives decoded JSON key strings, escape-equivalent keys are rejected as duplicates as well.

Existing non-standard numeric constant rejection remains active through the same parse call. Duplicate-key failures are `ValueError` subclasses and are normalized by `load_snapshot()` into the existing `SnapshotArtifactError` malformed/parser-safety path.

The helper is local and does not monkeypatch Python's global JSON decoder.

## Permanent regressions

Tests cover:

- duplicate root `capabilities` keys;
- duplicate nested `policy.deny` keys;
- duplicate keys that become equal only after JSON Unicode-escape decoding;
- the same field name appearing in two distinct JSON objects remaining valid;
- CLI `diff` failing closed with exit code 3 for a duplicate-key snapshot;
- the existing parser-recursion normalization test retargeted to the new loader boundary.

## Security effect

Externally supplied snapshots must now have one unambiguous value for each JSON object key before fingerprint and semantic validation begin. A malicious or malformed artifact can no longer rely on last-key-wins decoding to shadow security evidence inside the trusted diff path.

## Compatibility

Canonical snapshots generated by AgentCapDiff are unchanged. Older valid snapshots with unique keys and additive fields remain readable. Public snapshot structure, capability fingerprints, policy fingerprints, diff semantics, and package version remain unchanged at `1.0.0`.

Artifacts that rely on repeated keys inside a single JSON object are now rejected. Duplicate JSON keys are ambiguous input rather than a stable snapshot contract.

## Follow-up boundary

General discovery metadata still uses permissive JSON/YAML parsing and intentionally remains outside this audit. Hardening discovery duplicates requires a separate compatibility decision because discovery scans many unrelated repository data files and currently tolerates malformed documents rather than failing the whole scan.
